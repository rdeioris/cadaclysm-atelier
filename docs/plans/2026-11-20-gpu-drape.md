# Atelier: the live drape on the GPU

Date: 2026-11-20. Branch `gpu-drape` (from origin/main 9ed375a). Kernel: cadaclysm master 2ce20ae6bc, which landed the WGSL cloth backend on the web View (`View.showCloth`, `stepCloth`, `clothPositions`, `clothHealth`, `pinCloth`, `unpinCloth`, `dragCloth`, `setClothOptions`, `clothGpu`; source `crates/cadaclysm-wasm/src/view_cloth.rs`). Design: cadaclysm `docs/superpowers/specs/2026-11-19-atelier-cloth-gpu-design.md`; this is its "app switch" follow-up.

**Goal:** on a WebGPU browser the live drape runs on the View's GPU, at 30 fps or more for the sample T-shirt in Chrome. Elsewhere (WebGL2, or `?cloth=cpu`) the CPU cloth worker of M4b stays the path. Simulate / Pause / Reset, Pin, Drag, re-mesh on an outline edit, stale on other edits, health and fps work on both.

## Why the cloth moves into the View worker

`View.showCloth(handle)` reads a kernel cloth handle from the same wasm instance as the View, and the GPU writes the cloth's vertices straight into the View's vertex buffer. The cloth worker has its own wasm instance, so on the GPU path the cloth is built in the View's worker (`atelier-worker.js`, which already imports the kernel as `k` from the same `pkg/index.js`). The CPU path keeps its own worker: a CPU step blocks for ~90 ms.

## Design

### `gpu-drape.js` (new): the GPU host

`GpuDrapeHost` speaks the cloth worker's port protocol in-process, so `atelier-worker.js` keeps one code path (`clothPort.postMessage(...)`, `onCloth(...)`):

- in: `avatar`, `build {text, ops, run}`, `update {text, ops}`, `run`, `pause`, `reset`, `pin {vertex}`, `drag {vertex, target}`;
- out (to `onmessage({data})`): `topology`, `frame`, `state`, `pinned`, with the same fields as `cloth-worker.js`'s, plus `gpu: { item }` on `topology` and `positions: null` on `frame` (the GPU path never reads positions back per frame).
- It owns a `Drape` (cloth.js) on the View worker's kernel module and one View item from `viewer.showCloth(drape.h, { colour })`. The colour is the first pattern's fabric colour: one item per cloth, so pieces are not coloured apart and the selection accent does not show on the cloth (recorded in the README).

The step loop (one frame in flight):

```
while running:
    t0 = now
    n = viewer.stepCloth(id, 1)            // 0 while a round trip (weld, edit, positions) is in flight
    h = await viewer.clothHealth(id)       // resolves once that frame's GPU work is done
    frames += n
    if n: emit frame (health, ms = now - t0)
    sewing -> draping: weldedPairs >= seamPairs (both non-null), or seamPairs 0, or frames >= SEW_FRAMES:
        viewer.setClothOptions(id, kernel options with the stored gravity)
    stop on nonFinite > 0 or maxSpeed > MAX_SPEED (healthOf's rules), as the CPU path
    yield one task (a MessageChannel ping) so pause/pin/drag/update messages are read
```

The status the CPU path builds from `cloth_status` is built from the health: `[frames, vertices, triangles, seamPairs ?? 0, weldedPairs ?? 0, nonFinite, dropped, maxSpeed]`, so `healthOf` and `sewingDone` are shared. `maxSpeed` units are checked against the CPU's in Task 1 (both mm/s per the kernel; assert it in a Node test if the pkg exposes both, else in the browser run).

Edits go through the View, never straight to the kernel cloth (its state is stale between round trips):

- pin: `viewer.pinCloth(id, v, null)` (pinned where it is at the round trip), unpin `viewer.unpinCloth(id, v)`; the pin's link from `cloth_vertex_link` as now (topology only). Pinned vertices do not move, so their points are drawn from the positions read at the press.
- drag: `viewer.dragCloth(id, v, target | null)`.
- update (2D edit): pause stepping, `await viewer.clothPositions(id)` (a round trip: the kernel cloth gets the GPU state), then `drape.update(text, ops)`; if it re-meshed: `viewer.remove(id)` and `showCloth` again, then a `topology`. Latest wins, as in the cloth worker.
- build: `drape.build(...)` on the View worker's kernel, then `showCloth`. Reset: `viewer.remove(id)`, `drape.freeCloth()`.
- `positions()` (async, for picks): `viewer.clothPositions(id)`.

The GPU uploads the cloth with the intersection analysis (GIA) off, whatever the options say; the CPU path keeps it on. The 3D strip says which engine runs: `GPU · GIA off` (title: "WebGPU cloth; the global intersection analysis is not on the GPU yet") or `CPU`.

### `atelier-worker.js`

- After the View exists: `gpuCloth = viewer.clothGpu && !data.cpuCloth`. When true, `clothPort = new GpuDrapeHost(viewer, k, ...)`, `clothPort.onmessage = onCloth`, and a `clothPort` message from the page is ignored. `ready` carries `clothEngine: "gpu" | "cpu"`.
- `onTopology` with `t.gpu`: `sim.meshes = [{ item: t.gpu.item, id: null, verts: null, gpu: true, colour }]`, no per-pattern meshes; the vertex patterns kept for picks.
- `onFrame` with `positions === null`: no `setMeshPositions`.
- `tool3d` and `pick3d` on the GPU item: `positions = await clothPort.positions()`, then `nearestVertex` over all vertices; `pick3d` resolves the pattern from that vertex's pattern.
- `removeCloth` does not `viewer.remove` the GPU item (the host owns it).
- `simPost` adds `engine`.

### `atelier.js`, `index.html`

- The page creates the cloth worker (and the channel) only when `ready` says `clothEngine === "cpu"`.
- `?cloth=cpu` in the page URL forces the CPU path (`cpuCloth: true` in the canvas message), for the fallback test and for comparisons.
- A `#sim-engine` span in the 3D strip shows the engine text above; `#fps` keeps its format.

## Results (2026-11-20)

- Headless Chrome (WebGPU, D3D12/Dawn, RTX 3070), the app's sample T-shirt on f-M (2090 vertices, 3857 triangles), `ATELIER_FPS=1 node test/browser.mjs`, frames 60..180, the app's own rate (View drawing both viewports at the display rate):
  - GPU, two frames in flight: 28.4 / 28.3 / 28.2 fps, median **28.3 fps (35.3 ms/frame)**, CPU load 2-73% (other sessions' builds). Quieter runs earlier: 29.0, 29.1.
  - One frame in flight (Task 1's first loop): 25.2 fps.
  - CPU worker for scale (GIA on): 2.0 fps (489 ms/frame).
- The 30 fps goal is not met: the GPU frame alone is 31-33 ms (the kernel's cloth-gpu-fps page), the app's render adds ~3 ms. Weld round trips are not the cost (17 in 180 frames). Two sim frames per submit was probed once and not kept.
- At frame ~180 the GPU drape has 114/116 seam pairs welded, the CPU 116/116.
- Both browser runs (GPU, `ATELIER_CLOTH=cpu`) and `npm test` (22 files) green after the rebase onto 2d-on-view 6d21d2c. Screenshot: `D:/wt/atelier-shots/gpu-drape.png`.
- A drag on the GPU path waits for a positions readback at the press; a release before it lands now says so (the browser test holds the press 400 ms).
